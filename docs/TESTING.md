# Judge smoke test

## Model-backed latency evaluation

The reproducible browser evaluation is pinned to `openai:gpt-5.6-terra`:

```sh
npm run eval:browser
npm run eval:latency:check
```

The generated latency report separates semantic task success from strict trajectory efficiency and reports every case independently. The gate requires 100% semantic and trajectory success, zero retries, overall p50 at or below 10 seconds, overall p95 at or below 20 seconds, and complex-create p50 at or below 15 seconds.

## Compare a real ChatGPT run with the eval

This comparison starts with the page already loaded, so browser startup and navigation are excluded from both sides.

1. Copy the suggested prompt, which is sourced from the matching eval fixture.
2. In the demo page, use **Start real-run timing** immediately before submitting that prompt to ChatGPT.
3. After ChatGPT's final response appears, use **Stop real-run timing** immediately.
4. Classify the observed task result, then use **Download trace**.
5. Apply the downloaded trace to the JSON report for the matching eval case:

```sh
npm run eval:latency -- .evals/report-<timestamp>.json \
  --real-trace ~/Downloads/real-run-<id>.json
```

The resulting latency JSON keeps the repeatable eval statistics unchanged and adds `realRunComparison`. The comparison reports the manually observed start-to-finish duration gap, time before the first WebMCP tool call, cumulative tool time, non-tool time, and time from the last tool result to the manual stop marker. Browser startup and navigation remain excluded, but the manual markers include the user's submit/return reaction time because the page cannot observe ChatGPT's shell directly. Outcome classification happens after timing has stopped. The downloaded trace's case name and prompt must match the eval fixture or the comparison fails closed. Unverified or unsuccessful runs remain visible with a warning rather than being presented as an equivalent successful-task cohort.

Use this three-minute walkthrough to see the core WebMCP and accessibility features. No mouse is required.

## Setup

1. Open the app in a WebMCP-enabled Chromium browser with a browser agent or Model Context Tool Inspector connected.
2. Use a fresh, non-duplicated tab so the workflow starts at revision `0` with no change history.
3. Optional: start VoiceOver on macOS or NVDA on Windows before beginning.

## 1. Check keyboard access (30 seconds)

Press `Tab` once. Focus should land on **Skip to workflow workspace** with a visible outline. Activate it, then continue tabbing through the canvas.

You should encounter seven clearly named workflow nodes:

- **Node: New lead submitted**
- **Action node: Enrich company**
- **Condition node: Qualified lead?**
- **Action node: Create CRM opportunity**
- **Action node: Add to nurture campaign**
- **Action node: Manual review**
- **Node: Complete**

The **Zoom In**, **Zoom Out**, and **Fit View** controls are also keyboard accessible. With a screen reader, the page exposes a **Workflow editor** heading, a **Workflow canvas**, and a **Most recent change** heading.

## 2. Ask the agent to edit the workflow (60 seconds)

Give the connected agent this exact request:

> We’ve had leads disappear whenever company enrichment is unavailable. Update the workflow so those leads are not lost and can be handled by the sales operations team. Show me what changed.

The agent should discover the current revision and make one atomic edit. The application-authored receipt appears in **Most recent change** without moving keyboard focus.

Look or listen for:

- **Changed 1 connection.**
- A new failure route from **Enrich company** to **Manual review**.
- One concise receipt marked **completed**.
- **Reveal Enrichment unavailable** and **Undo** controls.

With VoiceOver or NVDA running, the change summary should be announced automatically while keyboard focus remains where the user left it. The receipt is proof generated by the application, not prose invented by the agent.

## 3. Verify agent-to-user focus handoff (30 seconds)

Ask the agent:

> Show me where failed enrichment is handled.

The agent should infer that **Manual review** is the relevant workflow node. The canvas should bring it into view, select it, and move keyboard focus to it. A screen reader should announce **Action node: Manual review**.

Then ask:

> Put keyboard focus on the Zoom In control.

When you return to the page and make your first keyboard or screen-reader interaction, focus should land on **Zoom In** exactly once. Later interactions should not pull focus back unexpectedly.

## 4. Reveal and undo without a mouse (60 seconds)

Return to the receipt, then use `Tab`, `Enter`, or `Space` to:

1. Activate **Reveal Enrichment unavailable** and confirm the canvas centers and selects the failure connection without moving focus away from the button.
2. Activate **Undo**.

After Undo:

- A screen reader announces **Undid the previous workflow change and restored 1 connection.**
- Focus moves to the new undo receipt heading.
- The Enrich company-to-Manual review failure route disappears, while the original qualification paths remain unchanged.
- A new receipt replaces the original receipt in the UI and records the undo.

## Pass criteria

The smoke test passes if the agent can discover, edit, reveal, focus, and undo through WebMCP; the app records deterministic receipts; and the complete interaction path works with only a keyboard, with meaningful names, stable focus, and live screen-reader announcements.
